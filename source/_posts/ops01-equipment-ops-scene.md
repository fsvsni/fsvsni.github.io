> 本篇目标：确立第二个项目 **equipment_ops（设备运维）** 的场景设定——它服务谁、有什么资料、回答什么问题，以及和系列一（企业知识库）有什么不同。

## 一、这个项目是什么

**设备运维智能助手**：面向工厂/运维部门，帮助一线巡检员、维修工程师、调度员回答设备巡检、告警处理、维修工单、配件更换等运维问题。

一句话：**让"设备出问题时该怎么处理"用自然语言就能查到答案。**

## 二、核心场景设定

| 维度 | 设定 |
|---|---|
| **场景 ID** | equipment_ops |
| **服务对象** | 巡检员 / 维修工程师 / 调度员 |
| **资料源** | inspection（巡检）/ alarm（告警）/ repair（维修）/ work_order（工单） |
| **典型问题** | "日检异常怎么升级""设备告警怎么处理""巡检项有哪些""配件更换流程" |
| **资料形态** | 巡检记录表 / 告警处理 SOP / 设备照片截图 / 工单规则 |

## 三、四个资料源详解

```
equipment_ops 场景
├── inspection  巡检记录：每日巡检项、巡检标准、异常记录
├── alarm       告警处理：告警等级、处理 SOP、升级路径
├── repair      维修资料：维修手册、故障代码、配件更换流程
└── work_order  工单规则：工单创建、流转、关闭、优先级
```

### 资料形态差异

| 资料源 | 形态 | 特点 |
|---|---|---|
| inspection | 巡检记录表（Excel） | 结构化、高频、逐日产生 |
| alarm | 告警处理 SOP（PDF/MD） | 规则化、分级、时效性强 |
| repair | 设备照片 + 维修手册 | 多模态、经验性 |
| work_order | 工单规则（MD/表格） | 流程化、状态机 |

## 四、典型问题与处理思路

| 员工问题 | 期望处理 |
|---|---|
| "日检异常怎么升级" | 检索 inspection/alarm → 给出升级路径 |
| "设备告警怎么处理" | 检索 alarm SOP → 按告警等级给出步骤 |
| "巡检项有哪些" | 检索 inspection 表 → 列出巡检项 |
| "配件更换流程" | 检索 repair/work_order → 给出更换流程 |

> 注意：设备运维问题**时效性强**——告警处理要快、要准确，错了可能影响生产安全。

## 五、为什么 RAG 适合设备运维

| 运维痛点 | RAG 的解法 |
|---|---|
| 告警 SOP 分散在多个文档 | RAG 检索聚合相关片段 |
| 新员工不熟故障处理 | 检索历史维修记录参考 |
| 巡检记录多而杂 | 语义检索定位相关记录 |
| 工单流转规则复杂 | 检索工单规则快速确认 |

## 八、RAG 三价值在设备运维的体现

1. **信息聚合**：告警处理要查的多份 SOP 一次聚合
2. **自然语言**：不用记工单系统命令，直接问"这个告警怎么办"
3. **知识沉淀**：维修经验沉淀为可检索知识，新人少走弯路

## 九、双链路在设备运维的落地

- **离线链路**：巡检表/告警SOP/维修手册 → 切分 → 向量化 → 入库
- **在线链路**：巡检员提问 → 意图识别 → 混合检索（按 source 过滤）→ 重排 → LLM 流式回答
