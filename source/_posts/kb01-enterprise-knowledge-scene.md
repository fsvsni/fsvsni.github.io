## 一、场景背景：公司内部的知识为什么"问不到"

我入职一家公司，发现制度文件散落各处：

- **HR 制度**在 PDF 里：入职流程、请假规则、考勤制度
- **财务制度**在 Excel/表格里：报销规则、审批额度、发票要求
- **IT 制度**在内部 wiki 里：VPN 连接、账号申请、故障排查

同事问一句"报销超 5000 要谁审批"，行政要翻半天文档；问"VPN 连不上怎么处理"，IT 要重复解释。这不是知识不存在，而是**知识没有被结构化地检索和利用**。

这就是我第一个项目的切入点：**企业知识库（enterprise_knowledge）问答助手**。员工直接提问，系统从内部制度资料里检索出准确答案，而不是让模型乱编。

## 二、场景设定：三类制度资料

定义"企业知识库"这个场景，第一件事是明确它有哪些资料、哪些问题：

| 维度 | 设定 |
|---|---|
| 场景 ID | `enterprise_knowledge` |
| 资料来源（sources） | `hr`（HR 制度）、`it`（IT 制度）、`finance`（财务制度） |
| 资料形态 | 制度 PDF / Markdown、FAQ CSV、部分表格 |
| 典型问题 | "入职流程有哪些步骤"（hr）、"报销超 5000 谁审批"（finance）、"VPN 连不上怎么处理"（it） |

在项目的 `scenario.toml` 里，这些设定会被写死成配置，成为该场景的"身份标识"。

## 三、为什么不用裸 LLM：三个致命问题

在没有 RAG 之前，直接让大模型回答企业内部问题会遇到三个核心问题：

1. **知识截止日期**：模型训练完成后，无法获取训练数据之后的新信息。公司制度是动态更新的，模型根本不知道最新版本。
2. **幻觉问题**：模型不确定时会"编造"看起来很合理但错误的内容。企业内部场景里，一个错误的报销流程回答可能引发真实损失。
3. **私有知识无法覆盖**：企业内部制度、流程、业务文档是私有数据，从未进入公开训练集，模型天然无法回答。

## 四、RAG 的解决思路：把"闭卷考试"变"开卷考试"

RAG（Retrieval-Augmented Generation，检索增强生成）的核心思路一句话：

> 用户提问 → 先从知识库中检索相关文档 → 把检索到的文档和问题一起发给 LLM → LLM 基于文档生成答案

可以把它理解成**开卷考试**：LLM 不再只靠记忆回答，而是可以"查阅"我们提供的资料后再作答。

RAG 的三个核心价值：

| 价值 | 说明 |
|---|---|
| **答案可溯源** | 每个回答都能追溯到具体的文档片段，员工可以点开原始制度确认 |
| **知识实时更新** | 更新知识库不需要重新训练模型，改制度→重新入库→立即生效 |
| **幻觉大幅减少** | 模型被约束在提供的文档范围内回答，而不是自由发挥 |

## 五、这套系统长什么样：两条核心链路

一个完整的 RAG 系统包含两条核心链路：

```
离线链路（入库）：
  文档加载(PDF/MD/Word/Excel) → 文档切分(父子块策略) → 向量化(BGE-M3) → 向量存储(Milvus Collection)

在线链路（问答）：
  用户提问 → 意图识别 → 语义检索(Dense+Sparse Hybrid) → 重排序(BGE Reranker)
  → 上下文构建 → LLM 生成(DashScope 流式输出) → 可溯源答案
```

### 离线链路（入库）：把制度变成可检索的知识

1. **文档加载**：读取 PDF、Markdown、Word 等各种格式的制度文档
2. **文档切分**：把长文档按语义边界切成小块（chunk），每块几百到一千字
3. **向量化**：用 Embedding 模型把每个 chunk 转成一串数字（向量），表达其语义
4. **存储**：把向量和原文一起存入向量数据库（Milvus）

### 在线链路（问答）：员工提问到获得答案

1. **意图识别**：判断用户问的是什么类型的问题（比如是问制度流程，还是闲聊）
2. **查询向量化**：把用户问题转成向量
3. **语义检索**：在向量数据库中找最相似的制度片段
4. **上下文构建**：把检索到的片段整理成 LLM 的参考资料
5. **答案生成**：LLM 基于资料生成回答

## 六、技术栈全景

这个场景的项目（KnowForge RAG Platform）技术栈如下：

| 层级 | 技术 | 作用 |
|---|---|---|
| API 框架 | FastAPI | 原生异步、WebSocket、自动 OpenAPI 文档 |
| RAG 编排 | LangChain | ChatModel、VectorStore、MessageHistory 封装 |
| 向量数据库 | Milvus 2.5.x | Dense + Sparse 混合检索 |
| Embedding | BGE-M3 | 中文语义强，1024 维 Dense 向量 |
| Sparse | Milvus BM25BuiltInFunction | 服务端内置，无需额外分词器 |
| Reranker | BGE Reranker Large | CrossEncoder 精细排序 |
| LLM | DashScope（OpenAI 兼容） | 通过 ChatOpenAI 统一调用 |
| 会话存储 | MySQL | SQLChatMessageHistory 管理表结构 |
| 缓存 | Redis + 进程内缓存 | 支撑检索与版本激活缓存失效 |

## 七、和"整个课件八大业务场景"的关系

这个平台是**多场景 RAG 平台**：内置 8 个行业场景，共享同一套核心引擎。`enterprise_knowledge` 只是其中之一，也是最主要的示例场景（贯穿课程大多数章节）。

其他场景包括：`saas_support`（SaaS 客服）、`equipment_ops`（设备运维）、`compliance_qa`（合规风控）、`cross_border_risk`（跨境贸易）、`tender_contract_risk`（招投标合同）、`insurance_claims`（保险理赔）、`engineering_project_qa`（工程项目）。

每个场景的区别主要在：**资料源（sources）、典型问题、检索倾向、Prompt 人设**。核心引擎（意图识别、检索、RAG 主流程、版本、隔离、质量）完全复用。
