> 对应课件：第 1 讲 2.2~2.6 节（全景架构、部署架构、技术栈、核心模块）
> 本篇目标：从**设备运维**视角讲清项目整体架构——离线入库、在线问答两条链路如何组织，四类资料源如何落到架构里。

## 一、一句话描述项目

这是基于 LangChain + Milvus 2.5 Hybrid Search 的多场景 RAG 平台。在 `equipment_ops` 场景下，它把**巡检记录、告警 SOP、维修手册、工单规则**变成可语义检索的知识，让运维人员用自然语言提问就能获得处理方案。

## 二、全景架构：两条链路

```
┌────────────── 离线链路（入库） ──────────────┐
│  巡检表/告警SOP/维修手册/工单规则              │
│    → 加载（表格/PDF/MD/图片OCR）               │
│    → 切分（父子块 + 表格专用）                 │
│    → 向量化（BGE-M3）                         │
│    → 入库（Milvus，按 source 分区）            │
└──────────────────────┬──────────────────────┘
                       │ 检索
┌──────────────────────▼──────────────────────┐
│  在线链路（问答）                              │
│  巡检员提问 → 意图识别 → 混合检索(Dense+BM25)  │
│    → 过滤(inspection/alarm/repair/work_order) │
│    → 重排 → 上下文 → LLM 流式回答              │
└─────────────────────────────────────────────┘
```

## 三、四条流式主链路（设备运维的独特之处）

企业知识库是"一条主链路"，但设备运维场景因为资料形态差异大，需要**四条**流式主链路：

| 链路 | 处理对象 | 用途 |
|---|---|---|
| **巡检链路** | inspection 巡检记录 | "巡检项有哪些""日检异常怎么办" |
| **告警链路** | alarm 告警 SOP | "告警怎么处理""要升级吗" |
| **维修链路** | repair 维修手册 | "故障怎么修""配件怎么换" |
| **工单链路** | work_order 工单规则 | "工单怎么创建""怎么关闭" |

```
用户提问
  → 意图识别（巡检/告警/维修/工单/其他）
  → 路由到对应链路
  → 该链路执行检索 + 生成
```

> 四条链路共享同一套 RAG 引擎，只是**场景配置、Prompt、检索参数**不同。这就是"一个引擎，多场景"的架构价值。

## 四、部署架构（与系列一相同的底座）

```
┌────────────────────── 宿主机 ──────────────────────┐
│  Docker Compose：                                    │
│   API │ MySQL │ Redis │ etcd │ MinIO │ Milvus       │
│   └─────┴───────┴───────┴──────┴───────┴─────┘      │
│   Local Models：BGE-M3 / BGE-Reranker / BERT意图     │
└──────────────────────┬──────────────────────────────┘
                       │ HTTPS
              ┌────────▼────────┐
              │ DashScope 云端LLM│
              └─────────────────┘
```

关键点：
- **本地模型**：向量化、重排、意图分类全程本地，运维数据不出内网
- **云端 LLM**：只有生成阶段走 DashScope
- **本地组件绑定 127.0.0.1**，不暴露公网

## 五、技术栈（与系列一共享底座）

| 层级 | 技术 | 在设备运维中的作用 |
|---|---|---|
| API | FastAPI | WebSocket 流式问答 |
| RAG 编排 | LangChain | 模型调用、向量库接口 |
| 向量库 | Milvus 2.5.x | 巡检/告警/维修/工单四类向量 |
| Embedding | BGE-M3 | 巡检记录、SOP 向量化 |
| 混合检索 | Dense + BM25 | 故障码精确 + 语义匹配 |
| Reranker | BGE Reranker | 故障相关文档精排 |
| LLM | DashScope | 生成处理步骤 |
| 会话 | MySQL | 多轮运维咨询历史 |
| 缓存 | Redis | 查询/检索/版本缓存 |

> 技术栈和设备运维的关系：**故障码需要 BM25 精确匹配**、**处理方案需要重排精排**、**实时告警咨询需要流式快答**——每项技术都有运维场景的落点。

## 六、核心模块与运维场景的映射

| 模块 | 在设备运维中的职责 |
|---|---|
| `intent` | 判断是巡检/告警/维修/工单问题 |
| `retrieval` | 按 source 过滤四类资料，混合检索 |
| `pipeline` | 四条链路的流式编排 |
| `prompts` | 巡检/告警/维修/工单各用不同模板 |
| `indexing` | 巡检表/图片/手册入库 |
| `governance` | 告警 SOP 版本管理、设备数据隔离 |
| `quality` | 入库质量检查、故障处理方案评测 |
| `scenarios` | equipment_ops 场景配置（4 sources） |

## 七、equipment_ops 场景配置落点

`scenario.toml` 中配置设备运维场景：

```toml
[scenario.equipment_ops]
sources = ["inspection", "alarm", "repair", "work_order"]
# 每个 source 的资料形态、检索权重、Prompt 模板
[scenario.equipment_ops.source.inspection]
form = "table"        # 巡检记录是表格
[scenario.equipment_ops.source.alarm]
form = "sop"          # 告警是流程文档
[scenario.equipment_ops.source.repair]
form = "manual"       # 维修是手册
[scenario.equipment_ops.source.work_order]
form = "rules"        # 工单是规则
```

> 四类 source 形态不同 → 入库切分方式不同、检索权重不同、Prompt 模板不同。

## 八、为什么设备运维需要"按 source 过滤"

巡检员问"日检异常" → 应该只查 inspection + alarm，不查工单规则。
调度员问"工单怎么建" → 应该只查 work_order。

**按 source 过滤**保证检索精准、回答聚焦，避免跨资料源噪声。
